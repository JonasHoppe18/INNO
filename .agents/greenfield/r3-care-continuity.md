# R3 care continuity vertical slice

An unresolved washing-machine question survives a product-identification follow-up in the existing Greenfield CaseState. The interpreter receives scoped pending read-only intent and classifies identification, a new request or explicit resolution. No new interpreter, planner or evidence validator is introduced.

## Lifecycle

1. Store recognized care facets and grounded qualifiers, with a missing/verification subject requirement. State is bounded to eight pending requests and a 1,000-character source quote. No evidence or operational snapshots are stored.
2. A current, grounded product-identification follow-up carries the original care request into existing precise-read recovery and coverage. An unrelated request suspends it. A different product or conflicting catalog ID cannot inherit a bound request.
3. Bind an unambiguous current verified product through the existing subject/source checks. Read care evidence again in the current scope.
4. Close only when every carried care facet has supported, satisfied, actually rendered coverage for that verified product, or when the customer explicitly resolves/abandons the request. An acknowledgement alone cannot close it.

## Limits

This is recognized product-care continuity, not durable handling of every support task. It cannot recover an initial question that TurnIR never registers, and it still depends on the existing interpreter classifying a subject follow-up. Unknown/unavailable care stays pending rather than being falsely marked answered. Bound subject aliases are conservative; ambiguous or changed identity does not inherit old work. There is no deployed DEV smoke yet.

Existing semantic evidence limitations remain unchanged. Semantic Contract V2 stays paused. No provider mutations, outbound sends, merchant Knowledge/fixture changes, sealed benchmark rerun, merge or deployment.
